## 1.操作系统的概念、功能

**没有操作系统 → 程序直接控制硬件，容易出错、冲突、危险（就像裸奔的嵌入式设备）**

**有操作系统 → 所有程序必须通过操作系统来申请资源、访问硬件，形成了控制、有序、安全的运行环境。**

---

![](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20240915005200289.png)



**CPU 只能直接访问内存,CPU 不能直接访问外存，必须通过 OS 的文件系统管理。**

OS 通过中断（I/O 中断、时钟中断）接管 CPU，实现进程调度、I/O 处理，没有中断就没有多任务操作系统。

- 是硬件向 CPU 发送的信号
- **是CPU 从「用户态」切换到「内核态」的唯一途径**

| 类别                      | 全称                | 触发原因                                  | 特点                                               | 例子                                           |
| ------------------------- | ------------------- | ----------------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| **外中断（中断）**        | 外部中断 / 异步中断 | CPU 外部的 I/O 设备、时钟等硬件发出的请求 | 与当前执行的指令无关，异步发生，可屏蔽             | 键盘输入、I/O 完成、时钟中断、网卡数据到达     |
| **内中断（异常 / 陷阱）** | 内部中断 / 同步中断 | CPU 执行指令时自身产生的异常              | 与当前执行的指令相关，同步发生，不可屏蔽（部分可） | 除零错误、缺页中断、非法指令、系统调用（trap） |

外中断是**被动的**：CPU 不知道什么时候会来，比如用户突然按键盘。

内中断是**主动的**：CPU 执行某条指令时必然触发，比如除零、系统调用。

系统调用本质是**内中断（trap 指令 陷入）**：用户程序主动触发，让 CPU 进入内核态，执行 OS 的系统服务。



CPU 在**每条指令执行结束时**（计组核心：中断响应的时机是**指令周期**结束），检测是否有中断请求。计组的周期 指令周期

什么是多道程序设计？
多道程序设计的核心思想是：在内存中同时存放多道（多个）独立的程序，让它们交替执行，共享 CPU 和系统资源
。
运行状态：从宏观上看，多道程序是并发运行的（它们都处于开始与结束点之间，都在运行过程中）；但从微观上看，单核 CPU 的执行是串行的（各道程序轮流占用 CPU，交替执行）
。
硬件基础：它的实现高度依赖两项底层硬件技术
：
中断处理：使得一个程序在未完成之前可以被打断，将执行权切换给其他程序。
I/O 通道技术（或 DMA）：把耗时且慢速的 I/O（输入/输出）操作交给专门的通道或控制器去完成，从而把 CPU 解放出来，让 CPU 去执行其他进程。

## 3.操作系统的发展和分类 核心在人速度 和 cpu快速之间的矛盾 

cpu 不得不等人 



| 阶段/类型      | 为什么设计                    | 解决什么问题                            | 优点                                | 缺点                                         |
| -------------- | ----------------------------- | --------------------------------------- | ----------------------------------- | -------------------------------------------- |
| 手工操作阶段   | 最早没有 OS，只能人工操作机器 | 让人能直接把程序交给机器运行            | 简单、直接                          | CPU 等人、等慢速 I/O，利用率极低             |
| 单道批处理     | 减少人工干预                  | 一批作业自动连续处理                    | 比手工阶段 CPU 利用率高             | 内存中只有一道作业，作业等 I/O 时 CPU 仍空闲 |
| 多道批处理     | 进一步提高 CPU 利用率         | 一个作业等 I/O 时，CPU 可运行另一个作业 | CPU 利用率高、吞吐量高              | 交互性差，用户不能及时控制作业               |
| 分时系统       | 让多个用户能交互使用计算机    | 批处理“不能及时交互”的问题              | 响应快、支持多用户、人机交互好      | 系统开销增加，吞吐量不一定最高               |
| 实时系统       | 对时间有严格要求的控制场景    | 必须在规定时间内响应外部事件            | 及时性、可靠性、可预测性强          | 设计复杂，资源利用率可能不是最高目标         |
| 网络操作系统   | 多台计算机联网共享资源        | 远程登录、文件共享、打印共享            | 资源共享、通信方便                  | 各机器相对独立，透明性较弱                   |
| 分布式操作系统 | 把多台机器组织成统一系统      | 用户不想关心资源在哪台机器              | 资源透明、统一管理、可靠性/扩展性好 | 实现复杂，同步、通信、一致性难               |
| 个人计算机 OS  | 面向个人桌面使用              | 普通用户需要易用、交互、图形界面        | 易用、交互强、应用生态丰富          | 早期多用户/安全/可靠性不如大型 OS            |


## 操作系统的体系结构



“操作系统体系结构”问的是：

```
这些模块应该放在哪里？
模块之间怎么调用？
哪些在内核态？
哪些在用户态？
```

原语是os最接近硬件的部分   

![image-20250722131916940](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250722131916940.png)



资源管理模块的大量管理逻辑是维护表、队列、控制块；
不是每一步都直接访问硬件。

**时钟管理**

要依赖硬件定时器：

```
设置时钟芯片/定时器
接收时钟中断
更新时间片
```

这直接和硬件有关。



**中断处理**

中断处理直接响应硬件事件：

```
键盘中断
磁盘中断
网卡中断
时钟中断
```

CPU 要跳到中断处理程序，内核要保存现场、处理中断源。

这明显贴近硬件。



**原语**

原语是内核中不可分割的小操作，要求：

```
一气呵成
不可中断
原子性
```

为了保证原子性，可能要：

```
关中断
开中断
使用硬件原子指令
```

所以原语也靠近硬件。





![image-20250722131351522](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250722131351522.png)

**微内核优缺点**

| 项目 | 内容       | 原因                          |
| ---- | ---------- | ----------------------------- |
| 优点 | 内核小     | 只保留最基本功能              |
| 优点 | 易维护     | 功能模块独立，结构清晰        |
| 优点 | 可靠性高   | 服务在用户态，故障隔离好      |
| 优点 | 易扩展     | 可以增加/替换用户态服务       |
| 优点 | 适合分布式 | 天然消息传递模型              |
| 缺点 | **性能低** | 频繁状态切换和消息传递        |
| 缺点 | 通信复杂   | 服务之间不能直接调用 频繁变态 |
| 缺点 | 实现复杂   | IPC、服务管理、同步都要设计好 |



**微内核为什么性能低**

**因为服务分散在用户态，模块之间不能直接函数调用，必须靠消息通信和状态切换。**

例如应用程序读文件：

```
应用程序
↓ 请求文件系统服务
文件系统服务
↓ 请求磁盘设备服务
设备服务
↓ 请求微内核调度/通信
微内核
↓ 返回设备服务
↓ 返回文件系统服务
↓ 返回应用程序
```

这就会发生多次：

```
用户态 ↔ 内核态
```

所以图里说：

```
微内核可能六次变态
```



每次状态切换都有成本：

```
保存现场
切换特权级
切换栈
检查参数
可能影响缓存/TLB
```

大内核把很多模块都放内核态，所以中间不用频繁来回切。



**大内核缺点**

因为很多东西都在内核里，一个模块出错可能拖垮整个系统。



![image-20250722131403276](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250722131403276.png)



**微内核为什么更安全、易维护**

因为很多服务在用户态运行。

例如文件系统服务崩了：

```
文件系统服务进程出错
↓
它是用户态进程
↓
理论上可以重启该服务
↓
不一定导致整个内核崩溃
```

微内核优点：

```
内核小
结构清晰
可靠性高
易维护
易扩展
```

![image-20250722131620843](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250722131620843.png)

都放内核里 → 快，但危险、难维护
都拆出去 → 安全、清晰，但慢
严格分层 → 清楚，但调用路径长
模块化 → 灵活，但依赖复杂

## 3.进程控制

简化理解：反正进程控制就是要实现进程状态转换	

**原语：**原子性的语句



父子进程 

一个程序要运行，通常需要已有进程去创建它。



`fork()` 的意思是：

> 复制当前进程，创建一个新的子进程。

fork() 在父进程中返回：子进程 PID
fork() 在子进程中返回：0
fork() 失败返回：-1



所以创建子进程，本质上是操作系统创建了一个新的进程实体。



那 fork 会不会真的把全部内存复制一遍？

现代操作系统一般不会立刻完整复制。

因为太浪费。

比如父进程用了 2GB 内存，如果 `fork()` 立刻复制 2GB，那开销爆炸。

所以现代系统常用：

```
写时复制 Copy-On-Write，简称 COW
```

意思是：

```
fork 刚发生时，父子进程先共享同一批物理内存页
但这些页被标记为只读
如果某一方要修改某页，系统才真正复制那一页
```

文件描述符继承

经典模型是：

```
父进程 fork 出子进程
子进程 exec 新程序
父进程 wait 等子进程结束
```

父进程为什么要 wait 子进程？

因为子进程结束以后，它不是立刻从系统里彻底消失。

操作系统需要保留一点信息给父进程看，比如：

```
子进程退出码
子进程是否异常终止
用了多少资源
```

父进程通过：

```
wait();
waitpid();
```

回收这些信息。

这个过程叫：

```
回收子进程
```





子进程已经结束了，但是父进程没有调用 `wait()` 回收它。

这时候子进程就变成：

```
僵尸进程 Zombie Process
```

它已经不运行了，也不占 CPU，但它的 PCB 还留在系统里。

为什么还留着？

因为里面有退出状态，等父进程来收。

状态是：

```
子进程死亡
但尸体还没被父进程收走
```

**父子进程之间怎么通信？**

因为父子进程地址空间独立，不能像线程一样直接共享变量。

所以要通过进程间通信 IPC。

常见方式：

```
管道 pipe
命名管道 FIFO
消息队列
共享内存
信号 signal
socket
文件
信号量
```

`wait()` 返回的是：

> **已结束子进程的 PID（进程号） + 子进程的退出状态（exit status）**

## 5.线程

一个**线程**是 CPU 调度的最小单位，它依赖进程而存在，**共享所在进程的资源**

**进程**是除CPU的系统资源分配的基本单元



![image-20250213194536141](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250213194536141.png)



![image-20250213194812056](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250213194812056.png)

> 操作系统真正安排上 CPU 运行的是“线程”，不是进程。**线程才有执行能力**，也叫执行单元。

- 每个线程有自己的寄存器、栈、**程序计数器（PC）**
- **线程运行时切换、阻塞、唤醒、调度，全部由操作系统的调度器（Scheduler）控制**





引入线程后：进程和线程分工了

有了线程以后，分工变成：

| 对象     | 主要作用          |
| -------- | ----------------- |
| **进程** | 资源分配单位      |
| **线程** | CPU 执行/调度单位 |

也就是说：

```
进程 = 资源容器
线程 = 真正干活的执行流
```

所以教材说：

> 线程是一个基本的 CPU 执行单元，也是程序执行流的最小单位。



![image-20250213195028533](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250213195028533.png)

**几乎不拥有！！！**



**注意线程切换的时候 切换的线程前后是否是在==同一个进程==当中**

一个线程属于某个进程，它并不会为自己申请一整套系统资源，而是使用“进程已经分配好的那一份”。 所以开销很小 ！！

✅ 线程共享的资源包括：

- **虚拟内存空间**（堆、代码段、全局变量等）
- **打开的文件描述符**
- **网络连接**
- **I/O 缓冲区**
- **信号处理器等**

✅ 线程**私有的内容**：

虽然线程共享进程的资源，它自己也有一些私有的部分，比如：

**局部的** 

- **栈（stack）**
- **寄存器（程序计数器 PC、通用寄存器等）**
- **线程 ID（TID）**
- **局部变量（保存在自己的栈中）**

----



**① 当前线程 A 时间片用完（或主动放弃 CPU）**

- CPU 产生**时钟中断**，操作系统中断处理程序进入。
- 保存线程 A 的所有寄存器状态（PC、SP、通用寄存器等）到**线程 A 的==内核栈==或==线程控制块（TCB）==**中。
- **更新线程 A 状态为“就绪”或“阻塞**”，放入对应队列。

**② 调度器开始选择下一个线程**

- **调度算法**选中线程 B。
- 从线程 B 的线程控制块（TCB）中读取寄存器状态，加载到 CPU 寄存器。
- 恢复线程 B 的堆栈指针和程序计数器。

**③ CPU 恢复运行线程 B**

- 线程 B 从上次停止的指令继续执行。
- 中断处理完成，返回到线程 B 的上下文。



 线程“私有”的核心只有一类：

> **CPU执行现场 + 运行上下文（execution context）**

也就是：

- 栈（stack）
- 寄存器（registers）
- 程序计数器 PC
- PSW（状态字）
- TID（线程标识）
- 线程栈上的局部数据



| 方面     | 同进程线程                         | 不同进程线程                       |
| -------- | ---------------------------------- | ---------------------------------- |
| 资源共享 | 共享进程内存和资源，通信简单快速   | 资源隔离，通信需进程间通信（IPC）  |
| 并发目的 | 实现应用内部并发，提高响应性和效率 | 实现多应用并发，提高系统多任务能力 |
| 调度单位 | 线程                               | 线程（线程属于不同进程）           |
| 开销     | 线程切换开销小                     | 进程切换开销大                     |

提高程序的并发性和效率，充分利用 CPU 资源，实现更灵活、快速的任务执行。

## 线程的实现方式和多线程模型

![image-20250213195128796](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250213195128796.png)

**多线程模型是 内核级线程和 用户级线程的联系**

用户级线程是程序自己“模拟/管理”的线程；内核级线程是操作系统真正知道、真正调度的线程。

**用户级线程缺点**

最大问题：

> **如果一个用户级线程阻塞，可能导致整个进程阻塞。**

比如：

```
进程 P 里有用户线程 T1、T2、T3
```

T1 发起阻塞式磁盘 I/O：

```
T1 等磁盘
```

因为内核只知道“进程 P 在等磁盘”，不知道 P 里面还有 T2、T3 可以继续跑。

于是可能变成：

```
T1 阻塞
整个进程 P 阻塞
T2、T3 也没法运行
```

**操作系统只能看到内核级线程**

## 6.调度

调度的本质： **资源不够 你们按顺序有序执行 并且要整体效率**

当有一堆任务要处理，但由于**资源有限，这些事情没法同时处理**。这就需要确定某种规则来决定**处理这些任务的顺序，这就是“调度”研究的问题**。

在操作系统中，**调度是管理进程执行的重要机制**，主要分为**高级调度**、**中级调度**和**低级调度**。这三种调度各自**负责不同层次**的任务，具体如下：

![image-20260625163229522](https://cdn.jsdelivr.net/gh/kasahuki/os_test@main/img/image-20260625163229522.png)

**==高级调度==** 

**定义**：高级调度（也称**作业调度**或长程调度）负责**从外存（如硬盘）中选择作业**，将其加载到内存中并为其分配必要的资源。

**功能与过程**：

- 选择后备队列中的作业，将其调入内存。
- 创建**进程控制块（PCB）**，以便管理进程的状态和资源。
- 决定何时将作业**从外存移入内存，通常依据系统的负载和资源可用性。**
- 调度频率较低，通常每几分钟进行一次。

**==中级调度==**

进程挂起 = 操作系统把进程“暂停运行”，并把它从内存移到外存（磁盘）保存起来。

**（把进程的“运行内容”从内存换出去，但进程的信息还在（PCB还在）。）**

**定义**：中级调度（也称**内存调度**或平衡调度）主要**负责在内存和外存之间交换进程**，以提高内存利用率和系统吞吐量。

**功能与过程**：

- 将暂时不能运行的**进程挂起**，并将其移至外存。
- 根据内存的使用情况和进程的状态，决定哪些挂起的进程可以重新调入内存。
- PCB常驻内存，以便于管理和监控进程状态。
- 调度频率中等，可能会在进程状态变化时频繁发生。

**==低级调度==**

**定义**：低级调度（也称**进程调度**或短程调度）负责在**就绪队列**中选择一个进程并将**CPU**分配给它。

**功能与过程**：

- 从就绪队列中选择一个进程，将处理器分配给该进程执行。
- 进行上下文切换**，保存当前进程的状态并加载新进程的状态**。
- 调度频率高，通常每几秒钟就会发生一次，以确保系统响应及时。

**在操作系统中，调度分为高级调度、中级调度和低级调度。以下是每种调度的实际例子：**

**高级调度**

**例子**：在一个批处理系统中，用户提交了多个作业（如数据处理、报告生成等）。这些作业首先存储在外存的**后备作业队列**中。高级调度的任务是从这个队列中选择一些作业，将它们加载到内存中并创建相应的进程。

- **具体过程**：
  - 用户提交作业A、B、C。
  - 操作系统根据设定的策略（如优先级、资源需求等）选择将作业A和B加载到内存中。
  - 为这两个作业创建进程控制块（PCB），并将它们放入就绪队列，准备竞争CPU资源。
  
  
  ~~~
  高级调度的“调出”
  
  这里的“调出”不是中级调度的 swap out。
  
  它指的是：
  
  作业完成后退出系统，撤销该作业对应的进程和 PCB。
  
  也就是：
  
  进程运行完成
     ↓
  作业完成
     ↓
  撤销进程、释放资源、撤销 PCB
  
  所以高级调度里的“一次调入，一次调出”说的是：
  
  作业被接纳进入系统一次
  作业完成后退出系统一次
  ~~~
  
  

中级调度

**例子**：**在一个多任务操作系统中，内存资源有限，某些进程可能暂时不能运行。**中级调度负责将这些暂时不需要的进程挂起，移至外存，以释放内存给其他需要执行的进程。

- **具体过程**：
  - 进程X正在运行，但由于内存不足，操作系统决定将进程Y挂起并移至外存。
  - 当内存有空闲时，操作系统再将进程Y调入内存，并修改其状态为就绪状态，以便可以再次执行。

低级调度

**例子**：在一个实时操作系统中，多个进程处于就绪状态等待CPU执行。低级调度负责从就绪队列中选择一个进程并将其分配给CPU。

- **具体过程**：
  - 就绪队列中有进程P1、P2和P3。
  - 操作系统使用轮转调度算法，首先选择进程P1分配CPU。
  - 当P1的时间片用完后，操作系统将其挂起，并选择下一个就绪的进程P2继续执行。

通过这三个层次的调度，操作系统能够高效地管理资源，提高系统性能和响应能力。

## 7.进程调度的时机、切换、过程与方式

<span style="font-size:1.6em;">**I/O中断的工作原理**</span>

1. **中断请求**：当外部设备完成I/O操作（例如，数据从硬盘读取完成），它会向**CPU发送一个中断请求信号**  **xxx 向cpu发起中断请求信号 就是 xxx中断**。这通常是通过I/O控制器实现的。
2. **CPU响应**：一旦CPU接收到中断信号，它会暂时停止当前正在执行的程序，并保存其状态，以便稍后恢复。
3. **执行中断处理程序**：CPU转向预先定义的中断处理程序，执行相应的代码以处理该I/O操作的结果。例如，它可能会将读取的数据从内存中的缓冲区移动到用户程序指定的位置。
4. **恢复执行**：处理完中断后，CPU会恢复之前被中断的程序，从它停止的地方继续执行

CPU（中央处理器）几乎是无时无刻都在运行的。这是因为操作系统和应用程序需要不断地执行指令来完成各种任务，从处理你的输入输出请求到运行应用程序和维护系统的基本功能。即使你的计算机看似闲置，CPU 也会持续地执行一些基本的任务，**例如维护系统时钟和处理后台进程**。这种持续运行的状态保证了计算机能够随时响应你的操作和需求。

*计组部分知识

**零地址指令**（Zero Address Instruction）是一种计算机指令格式，它不需要显式地指定操作数或操作数的地址（也就是不需要访存）。相比之下，其他指令格式可能需要指定一个或多个操作数的地址或寄存器。零地址指令通常设计用于栈式计算机或者某些指令集体系结构中，其中操作数可以隐含地从栈顶或者特定的寄存器中获取。

在**零地址**指令中，指令本身包含了足够的信息来执行操作，而不需要额外的操作数地址信息。这种设计简化了指令的格式和编码，同时也能够加快执行速度

## 10.==调度算法==

 ![ ](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250215214540708.png)

**==作业==提交阶段**：

- 用户提交一个作业（如一个程序任务）给操作系统。
- 作业被放置在**==外存后备队列==**中等待。

**调度阶段**：

- 操作系统从外存后备队列中选择一个作业。
- 选择的标准可能包括作业的优先级、资源需求等。

**进程创建阶段**：

- 选中的作业被加载到内存中，操作系统为其创建一个或多个进程。
- 每个进程被分配到相应的内存空间，并分配执行所需的资源。

**执行阶段**：

- ==进程==被放置在==就绪队列==中，等待处理器的分配。 
- 一旦处理器可用，操作系统会从就绪队列中选择一个进程，将其调度到处理器上执行。

**执行结束及资源释放**：

- 进程执行完毕或者被中断后，操作系统可能将其从处理器移除**，并释放相关资源。**

- 结束的进程的状态可能会被更新并记录，然后可能将结果返回给用户或者存储到外存

  

  ---

  

  **IO中断会唤醒阻塞进程**是因为阻塞进程在执行IO操作时需要等待外部设备（如硬盘、网络接口等）完成特定的IO操作，这期间进程无法继续执行其他任务，处于阻塞状态。当外部设备完成IO操作并触发了IO中断时，操作系统会进行以下处理：

  1. **中断处理程序**：
     - 当设备完成 I/O 操作后，会通过**中断机制通知 CPU；**CPU 响应中断后，保存当前进程现场，转入操作系统内核，执行相应的中断处理程序。
     - 操作系统会调用与该IO操作相关的中断处理程序（IRQ处理程序），该程序会处理中断并根据中断的类型进行相应的处理。
  2. **唤醒阻塞进程**：
     - 如果阻塞进程是因为等待某个IO操作而阻塞的，中断处理程序会根据进程的状态将其从阻塞状态转换为就绪状态(队列、pcb)（Ready）。
     - 这意味着操作系统认为进程现在可以继续执行，因为所需的IO操作已经完成。
  3. **状态转换**：
     - 一旦进程被唤醒并放入就绪队列，操作系统的**调度程序会在适当的时候将其调度到CPU上执行。**
     - 进程在恢复执行后可以继续处理IO操作的结果或者执行接下来的任务。

注意非抢占式调度算法：

非抢占式调度算法通常通过进程主动放弃CPU或者在IO等待时让出CPU，而不会被操作系统强制剥夺CPU资源。

这种调度方式可以带来一定程度的**同步效果**，因为**进程的执行是有序的，一个进程执行完毕或者等待IO时，另一个进程才能开始执行。**

| 平均带权周转时间 | 所有带权周转时间之和 / 进程数 | 整个系统对长短作业是否公平     | 越小越好，越接近 1 越好 |

## 多级队列调度算法

![image-20250225191435938](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250225191435938.png)



**多级队列调度**
将进程分成多个固定队列，每个队列对应一个优先级。
队列中的进程优先级是静态的，不会在不同队列间移动。
调度器按照优先级顺序调度队列中的进程，高优先级队列中的进程先被调度。



**多级反馈队列调度**
允许进程在不同队列之间移动，优先级是动态调整的。
一个进程执行完一个时间片后，如果没有完成任务，会被移动到低优先级的队列中。
通过降低长时间运行进程的优先级，实现更加公平的资源分配和防止某些进程长期占用CPU资源。

#### 中断屏蔽方法

![image-20250302192254658](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302192254658.png)

“关中断”指的是**当前处理器**暂时不响应外部中断（如时钟中断、I/O 中断等），通常通过指令如 `cli`（x86）来实现。这是保护临界区的一种手段。

为什么**多核系统**不适用：

**单核环境下**：关闭中断后，该核心不会被其他中断抢占，能确保临界区的独占执行。

**多核环境下**：中断屏蔽仅作用于当前核心**，==其他核心==仍然可以响应中断并访问共享资源**。例如：

- 核心A屏蔽中断后进入临界区，但核心B未屏蔽中断，**仍可能通过中断或直接访问同一共享资源，导致数据竞争。**



---

以下两个硬件指令只能一气呵成 ！！！



#### TestAndSet指令

**TestAndSet = 原子地“看锁原来的值 + 把锁设为 true”，如果返回 false 说明原来没锁，抢锁成功；返回 true 说明原来有锁，继续忙等。**



TestAndSet 的本质是：

```
先测试锁原来的状态
然后无论如何都把锁设置为 true
最后返回锁原来的状态
```

![image-20250302192645556](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302192645556.png)

**没锁上** lock = false 返回false 设置lock = true 上锁 

**锁上** lock = true 返回 true 一直死循环判断 



---



#### Swap指令

**：我拿自己的 `true` 去和 `lock` 交换，换回来 `false` 就说明原来没锁，我成功上锁；换回来 `true` 就说明原来有锁，我继续等。**

~~~
如果临界区没人占用

初始：

lock = false    // 没人占用临界区
old  = true     // 我准备去尝试抢锁

执行：

Swap(&lock, &old);

交换后：

lock = true     // 我把锁设上了
old  = false    // old 得到了 lock 原来的值 false

然后判断：

while (old == true)

现在：

old = false

所以跳出循环，进入临界区。
~~~



![			](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302192855185.png)

swap的逻辑其实就是再上锁 



swap 和 tsl

目标完全一样：

> **都要把“检查锁是否空闲”和“把锁设为占用”合成一个不可分割的原子操作。**



Swap 和 TSL 本质都像“查看旧锁值并顺手上锁”。如果旧值是 false，说明没被占，我成功进入；如果旧值是 true，说明已经被占，我继续等，而且锁仍然保持 true，不会被我弄坏。

![image-20250302193923294](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302193923294.png)

在原子操作执行的过程中，**中间不可被插入其他操作**。这意味着，当一个线程执行原子操作时，其他线程不能中途插入任何操作（比如修改变量或访问共享资源）



**1.原子操作:**信号量的 wait 和signal操作是原子的。这意味着这些操作要么完全执行，要么完全不执行，避免了竞态条件。操作系统在实现这些操作时通常会使用**硬件提供的原子指令**来确保操作的不可分割性，

**2.硬件支持:**现代处理器提供了各种原子指令(如 compare-and-swap  （ **CAS** 操作是通过硬件指令来实现的，而不是通过软件模拟）或test-and-set )来支持同步原语的实现。这些指令可以确保在多处理器环境下，同时只有一个处理器能修改信号量的值，从而避免了并发修改的问题。

**3.锁机制:**在信号量的实现中，通常会使用**底层的锁来保证对信号量计数值的修改是互斥的。这样，当一个线程在进行 wait 或 signal操作时，其他线程会被阻塞，直到当前操作完成。**  wait 和 wait w 与 s s与s 之间都是**互斥的！**

### ==死锁（重点）==

**预防死锁：提前把“死锁产生条件”破坏掉，让死锁根本不可能发生。**
 **避免死锁：条件可以存在，但每次分配资源前先判断，会不会把系统推向危险状态；危险就不分配。**

![image-20250302201312448](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302201312448.png)

#### 死锁产生的四个必要条件

| 条件               | 在例子里的体现                                               |
| ------------------ | ------------------------------------------------------------ |
| **互斥条件**       | 打印机 A、扫描仪 B 一次只能被一个进程使用 (就是我只能从你那拿) |
| **不剥夺条件**     | P1 拿到 A 后，系统不能强行抢走 A；P2 拿到 B 后，也不能强行抢走 B （无法被外力抢夺） |
| **请求和保持条件** | P1 已经拿着 A，又请求 B；P2 已经拿着 B，又请求 A（有了对方要的，但是我还要对方持有的） |
| **循环等待条件**   | P1 等 P2 的 B，P2 等 P1 的 A，形成环（a要b持有的，b要a持有的，双方都不放 ） |

- **请求并保持条件是指：**

进程已经占有了一些资源，同时又去请求新的资源，并且在等待新资源时不释放旧资源。
方法 1：一次性申请所有资源
方法 2：申请新资源前，先释放已有资源

---



- **循环等待条件是指：**

存在一个进程等待环。
怎么破坏？

给所有资源编号，规定进程必须按照编号从小到大申请资源。 （不能反过来 也就是不能有依赖环产生 ）

#### 检测和解除

~~~
资源分配图：
圆形是进程，方形是资源，小圆点是资源实例。
进程 → 资源：请求边。
资源 → 进程：分配边。

死锁检测：
找一个“当前请求能被满足”的进程；
假设它执行完成并释放资源；
删除它所有相关边；
重复这个过程。

如果最后所有边都能删掉：
资源分配图可完全简化，没有死锁。

如果最后还有边删不掉：
资源分配图不可完全简化，剩下连着边的进程就是死锁进程。

死锁解除：
资源剥夺法、撤销进程法、进程回退法。

选择牺牲谁：
看优先级、已运行时间、剩余时间、占用资源数、交互/批处理类型。
~~~

 **recollect ：**<span style="font-size:1.7em; font-weight:bold; color:#FF0000;">进程的分类</span>

<span style="font-size:1.7em; font-weight:bold; color:#FF0000;"> **一、按运行特性与调度需求分类**</span>

1. **批处理进程（Batch Process）**

- **定义**：无需用户交互，按预定任务队列批量执行的进程。
- **特点**：
  - 以作业（Job）为单位提交，顺序执行。
  - 通常处理大量计算或数据处理任务（如科学计算、日志分析）。
  - 优先级较低，注重吞吐量而非实时性。
- **例子**：银行对账系统、批量图像渲染。

2. **交互式进程（Interactive Process）**

- **定义**：依赖用户输入并实时响应的进程。
- **特点**：
  - 需要频繁的I/O操作（键盘、鼠标、屏幕输出）。
  - 响应时间短（通常 < 1秒），优先级较高。
- **例子**：文本编辑器、命令行终端、图形界面应用。

3. **实时进程（Real-Time Process）**

- **定义**：必须在严格时间限制内完成任务的进程。
- **特点**：
  - 分为**硬实时**（绝对不可错过截止时间，如火箭控制）和**软实时**（允许偶尔延迟，如流媒体）。
  - 优先级最高，抢占其他进程资源。
- **例子**：工业机器人控制、自动驾驶系统、音视频实时编码。



---



<span style="font-size:1.7em; font-weight:bold; color:#FF0000;">**二、按功能角色分类**</span>

4. **守护进程（Daemon Process）**

- **定义**：后台长期运行的服务进程，通常无用户界面。
- **特点**：
  - 随系统启动而运行，响应特定事件或请求。
  - 资源占用低，生命周期长。
- **例子**：Web服务器（Nginx）、数据库服务（MySQL）、系统监控工具（Prometheus）。

5. **系统进程 vs 用户进程**

- **系统进程**：
  - 由操作系统内核直接管理，执行底层任务（如内存管理、进程调度）。
  - 例子：`systemd`（Linux初始化进程）、`kswapd`（内存交换守护进程）。
- **用户进程**：
  - 由用户启动，运行应用程序（如浏览器、办公软件）。



---



**<span style="font-size:1.7em; font-weight:bold; color:#FF0000;">三、按调度优先级与交互模式分类</span>**

6. **前台进程（Foreground Process）**

- **定义**：占用终端或用户界面，直接与用户交互。
- **特点**：
  - 优先级高，需即时响应用户操作。
  - 执行期间会阻塞终端输入（如编译任务在前台运行时无法输入其他命令）。

7. **后台进程（Background Process）**

- **定义**：脱离终端或界面在后台运行。
- **特点**：
  - 通过`&`符号启动（如`python script.py &`）。
  - 用户可继续执行其他任务，但可能受资源竞争影响。

是指计算机系统中**一次只能执行一个程序**的操作环境。在这种环境下，系统资源(如处理器、内存等)完全专用于当前运行的程序，直到程序执行完毕或被终止后，才会切换到另一个程序执行。这种环境通常用于早期计算机系统和某些嵌入式系统中。虽然单道程序环境简单，但在现代多任务操作系统中已不常见，因为它无法充分利用现代计算机的多核处理能力和资源共享功能。



#### 装入的三种方式

##### 绝对装入：

**绝对装入的本质是**

> **编译/链接时就把程序里的地址全部改成真正的物理地址。**

![image-20250302202931960](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302202931960.png)



~~~
那为什么说绝对装入只适合单道程序环境？

因为多道程序环境下，内存里有很多进程。

你很难提前确定：

这个程序一定从物理地址 100 开始放

万一地址 100 那块已经被别的进程占了呢？
san
那这个程序就没法按原计划装入。

所以绝对装入很死板：
~~~



##### 可重定位装入 / 静态重定位

程序编译时不知道自己将来会被放到内存的哪个物理位置，所以先统一使用从 0 开始的逻辑地址；等真正装入内存时，再一次性把这些逻辑地址改成物理地址。静态的意思就是：**装入时改完，运行时不再变。**

![image-20250302202939467](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302202939467.png)

**绝对装入：程序在编译/链接时就已经写死“我要访问物理内存的哪个地址”。**
 **可重定位装入：程序先使用逻辑地址，等真正装入内存时，再统一把逻辑地址改成物理地址。**



##### 动态重定位 （运行时）

程序运行时，指令里仍然使用逻辑地址；CPU 每次真正访问内存时，再由硬件把逻辑地址转换成物理地址。

![image-20250302202946958](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250302202946958.png)

1. 重定位寄存器
2. 逻辑地址
3. 加法器 / 地址转换机构



~~~
静态重定位是这样：

装入时直接修改指令：

79 → 179

程序运行时，指令里已经是：

访问 179

所以运行期间程序不能随便移动。

动态重定位是这样：

指令里一直保留：

访问 79

运行时才算：

100 + 79 = 179

如果以后程序被移动到物理地址 500 开始，只需要把重定位寄存器改成 500：

500 + 79 = 579

程序里的指令不用改。

这就很灵活。
~~~

**静态链接:**

**过程:**在编译阶段，所有需要的 	库文件和外部函数代码都会被链接器打包到可执行文件中。这样生成的可执行文件是自包含的.不需要依赖外部的库文件

**优点:**运行时不需要额外的库文件，因此避免了找不到库文件的问题，并且加载速度较快。

**缺点**:生成的可执行文件较大，并且更新库文件时需要重新编译整个程序。

---



**装入时动态链接(Load-timedynamic linking):**

**链接时间:**在程序启动时进行链接。操作系统会在加载可执行文件时，寻找并加载所需的动态链接库(DLL)过程:当程序启动时，操作系统会加载所有需要的DLL，并将外部函数的地址绑定到程序中。这意味着在程序开始运行之前，所有的链接和加载操作已经完成。

**优点:**程序启动后，不需要再进行动态加载，减少了运行时的开销。
**缺点:**如果程序依赖的某个DLL缺失或版本不兼容，程序可能无法启动

---



**运行时动态链接(Run-time dynamiclinking)**

**链接时间:**在程序运行过程中(根据需要动态加载库文件和链接外部函数。
过程:程序在运行时可以根据需要调用特定函数来加载DLL(例如LoadLibrary函数)，并使用函数指针来调用DLL中的函数。这种方式使得程序可以在运行时灵活地加载和卸载DLL。
**优点:**可以按需加载DLL，减少初始启动时的开销，提高程序的灵活性。只有在需要时才加载相应的DLL，有助于节省内存。

**缺点:**运行时需要额外的管理代码，处理加载和卸载DLL的操作。如果加载过程出错，可能会导致程序在运行中断。

---

| 对比维度       | 链接方式           | 解决的问题                                                   | 装入方式                        | 解决的问题                                     | 共同思想              |
| -------------- | ------------------ | ------------------------------------------------------------ | ------------------------------- | ---------------------------------------------- | --------------------- |
| **提前确定**   | **静态链接**       | 程序运行前，把所有目标模块和库函数全部链接成一个完整可执行文件 | **绝对装入**                    | 编译/链接时就生成绝对物理地址                  | **运行前全定死**      |
| **装入时确定** | **装入时动态链接** | 程序装入内存时，边装入边链接需要的模块/库                    | **可重定位装入 / 静态重定位**   | 装入内存时，把逻辑地址统一转换成物理地址       | **装入时再处理**      |
| **运行时确定** | **运行时动态链接** | 程序运行过程中，用到某个模块/库时才链接                      | **动态重定位 / 动态运行时装入** | 程序运行时，每次访存再把逻辑地址转换成物理地址 | **用到/执行时再处理** |

| --------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| 核心目的        | 防止进程访问自己范围外的物理内存                 | 同时完成**地址转换**和**内存保护**                           |

| 寄存器里存什么  | 下限：进程起始物理地址；上限：进程结束物理地址   | 重定位寄存器：进程起始物理地址；界地址寄存器：最大合法逻辑地址 |

| 判断条件        | `下限 ≤ 物理地址 ≤ 上限`                         | `逻辑地址 ≤ 界地址寄存器`                                    |
| 合法后怎么做    | 直接访问该物理地址                               | `物理地址 = 重定位寄存器 + 逻辑地址`                         |
| 非法时          | 产生越界异常                                     | 产生越界异常                                                 |
| 图中例子        | 进程 1 的物理地址范围是 `100 ~ 279`              | 重定位寄存器 = `100`，界地址寄存器 = `179`                   |

| 优点            | 直观，直接保护物理地址范围                       | 更适合动态重定位，逻辑地址不用提前改成物理地址               |
| 本质            | 保护：你只能访问自己的物理内存区间               | 地址转换 + 保护：先看逻辑地址越不越界，再转换成物理地址      |

#### 交换技术

~~~markdown
注意，交换技术一般是：

以进程为单位换入换出

也就是整个进程搬出去。

这和虚拟内存不同。

虚拟内存通常是：

以页为单位换入换出

这个区别很重要。
~~~

有交换技术之后，进程状态从**“五状态模型”**扩展成“带挂起的**七状态模型”。**

激活 = 把挂起进程重新调入内存。

~~~
为什么阻塞挂起能到就绪挂起？

先拆开看：

阻塞挂起 = 正在等事件 + 不在内存

它有两个问题：

1. 它在等事件，所以不能运行
2. 它被换出到外存，所以不在内存

现在“事件出现”了。

比如磁盘 I/O 完成了。

那么第一个问题解决了：

不再等事件了

所以它从“阻塞”变成“就绪”。

但是第二个问题还没解决：

它仍然不在内存

所以不能直接变成“就绪态”，只能变成：

阻塞挂起 → 就绪挂起

也就是：

事件完成了，但进程还在外存	
~~~

~~~
动态分区分配会产生很多分散的小空闲块。虽然这些空闲块加起来可能够大，但因为进程通常需要一整块连续内存，所以不能直接使用。
紧凑技术的做法：
把内存中已经装入的进程整体搬移，让它们尽量靠在一起，把原来分散的小空闲区合并成一整块大的连续空闲区。
例如原来是：
进程A | 空闲5MB | 进程B | 空闲8MB | 进程C | 空闲7MB
总空闲是 20MB，但分散了，可能放不下一个需要 18MB 连续空间的进程。
紧凑后变成：
进程A | 进程B | 进程C | 空闲20MB
这样就能放入需要连续空间的新进程。
它解决的是 外部碎片，不是内部碎片。
代价是：需要移动进程在内存中的位置，所以系统必须支持 动态重定位，并且搬移本身有时间开销。
~~~



### ==动态分区分配算法==

**凡是要求连续分配、会产生外部碎片的内存管理方式，都可能需要紧凑；动态分区是最典型代表。**	

| 算法     | 更看重什么         | 代价               |
| -------- | ------------------ | ------------------ |
| 首次适应 | 查找速度           | 低地址容易碎       |
| 最佳适应 | 本次分配尽量少浪费 | 产生很多小碎片     |
| 最坏适应 | 避免留下太小碎片   | 大空闲区被快速消耗 |
| 邻近适应 | 分配位置更均匀     | 整体可能更分散     |

**内存里有很多“空闲坑”，来了一个进程，要决定“把它放进哪个坑”。**

## 基本==分页存储管理==的概念

**页（进程）  ↔  页框（内存）**

**页表：**

| 页号 | 页框号 |
| ---- | ------ |
| 0    | 3      |
| 1    | 6      |
| 2    | 4      |
| 3    | 8      |

逻辑地址 = (页号, 页内偏移)

⭐ 页号：

```
页号 = 逻辑地址 / 页大小
```

⭐ 页内偏移：

```
偏移 = 逻辑地址 % 页大小
```

**分页(一维地址空间)**
分页机制中的，程序员只需要提供一个记忆符(通常是一个线性地址)，操作系统会负责将这个线性地址映射到物理内存地址。这里的用户地址空间看起来是一个连续的内存区域，但实际上可能分布在不同的物理内存页中。
例子: 假设程序员需要访问内存地址0x1234，这个地址是线性的。操作系统通过页表将0x1234映射到实际的物理内存地址，例如OxABCD。

---



**分段(二维地址空间)**
在分段机制中，用户进程地址空间是二维的。这意味着程序员在引用内存地址时不仅需要提供段名，还需要提供段内地址。每个段表示一个独立的内存区域，可能包含特定类型的数据，例如代码段、数据段和堆栈段。



**进程和段表的关系：**

进程和段表在操作系统中有着密切的关系。进程是程序在系统中的一次执行活动，它包含了程序计数器、寄存器、堆栈、数据段等。而段表是操作系统用来管理段式内存的一种数据结构。
段表记录了进程的每一个段的信息，包括段的起始地址、段的长度、段的权限等。它帮助操作系统将进程的逻辑地址转换成物理地址，以便对内存进行有效管理。每个进程都有一个独立的段表，通过段表，操作系统可以实现内存保护和共享，提高内存利用率。
可以将段表看作是进程的内存地图，帮助操作系统跟踪和管理进程所使用的各个内存段。因此，段表对于进程的内存管理至关重要。

---

## ==虚拟内存==的基本概念

~~~
程序 → 怎么装入内存？
        ↓
连续分配：简单粗暴，一个进程占一整块连续内存
        ↓
问题：外部碎片、内存利用率低、进程必须整体装入
        ↓
分页 / 分段：允许进程拆开存，解决连续空间要求
        ↓
问题：虽然能拆开，但程序仍然可能很大，内存仍然不够
        ↓
虚拟内存：不用一次性全部装入，用到哪部分再调入哪部分
        ↓
问题：内存满了，新页面进来，旧页面谁出去？
        ↓
页面置换：选择一个页面换出，给新页面腾位置
~~~



**分页/分段之后，为什么还要虚拟内存？**

分页解决了“不连续”的问题。

但是它还没有解决一个更狠的问题：

> **程序必须全部装入内存，才能运行。**

比如程序很大：

```
程序大小：10GB
物理内存：4GB
```

如果要求全部装入，那根本跑不了。

但实际运行时，程序通常不会同时用到全部代码和数据。

## ==请求分页管理方式==

按需调页。需要某一页时，如果它不在内存，就产生缺页中断，再把它从磁盘调入内存。

~~~
页 5 不在内存
CPU 访问页 5
↓
MMU 查页表
↓
发现页表项有效位 = 0
↓
发生缺页中断
↓
操作系统介入
↓
从磁盘把页 5 调入内存
↓
修改页表
↓
重新执行刚才那条指令
~~~

## 页表项里通常有什么？

请求分页里，页表项不只记录页框号，还可能有：

| 字段            | 作用                     |
| --------------- | ------------------------ |
| 页框号          | 该页在物理内存的哪个页框 |
| 有效位 / 存在位 | 该页当前是否在内存       |
| 访问位          | 最近是否被访问过         |
| 修改位 / 脏位   | 页面是否被修改过         |
| 权限位          | 可读、可写、可执行       |
| 外存地址        | 不在内存时，它在磁盘哪里 |

请求分页会带来一个新问题：

> 需要调入新页面时，内存可能已经满了。 

所以需要置换算法 

| 算法               | 思想                                                         |
| ------------------ | ------------------------------------------------------------ |
| OPT 最佳置换       | 淘汰未来最长时间不会用的页面，理论最优，但实际无法提前知道未来 |
| FIFO 先进先出      | 最早进入内存的页面先淘汰                                     |
| LRU 最近最久未使用 | 淘汰最近最长时间没被访问的页面                               |
| CLOCK 时钟算法     | LRU 的近似实现，用访问位判断页面是否最近用过                 |

## ==页面置换算法==

~~~
页面置换 = 内存满了，选一个页出去

           选谁？
             │
 ┌───────────┼────────────┐
 │           │            │
看未来      看过去        看成本
OPT         LRU           CLOCK
理论最优    实用思想       近似 LRU
 │           │            │
未来最久不用 最近最久没用 访问位为0
             
还有一个简单粗暴：
FIFO = 谁先来谁先走
~~~

## ==文件的物理结构（文件的分配方式）==

> **文件已经被用户看成一串逻辑块了，现在操作系统要解决：这些逻辑块到底放到磁盘哪些物理块里？**

也就是：

文件逻辑块号→磁盘物理块号\boxed{\text{文件逻辑块号} \rightarrow \text{磁盘物理块号}}

这部分408最核心就三大类：

> **连续分配、链接分配、索引分配**

> **① 能不能随机访问　② 文件扩展方不方便　③ 为了记录块位置，要付出多少额外空间/访盘次数**

### 阻塞/非阻塞IO

**阻塞 I/O 和非阻塞 I/O 的底层区别，不在设备怎么传数据，而在“数据没准备好时，内核如何处理当前进程”。**

**阻塞 I/O（Blocking I/O）**

**特点：**

- 进程（线程）在执行 I/O 操作时，如果数据没有准备好，会一直等待，直到 I/O 操作完成后才返回。
- 期间进程会被挂起，操作系统会调度其他进程执行，直到 I/O 操作完成后，该进程才会被重新调度执行。

### 设备驱动程序接口

**设备独立的系统调用标准在同一个操作系统中是否一致?**

同一个操作系统通常提供设备独立的标准接口来对外暴露统一的操作方法，这种抽象让应用程序不需要直接与硬件打交道。例如:
文件系统操作:无论是读取硬盘、U盘还是网络存储设备，调用方式在应用程序层面可能只是一个统一的
read()或write()。

尽管**接口标准一致**，但某些地方可能因设备差异而有所不同:

**底层驱动的实现方式不同:**

比如硬盘的读写和网络存储设备O的读写虽然在调用层面是一致的，但驱动程序实现上会根据硬件差异而有所不同。
某些设备可能具有专属功能，这些功能需要额外的控制命令

**硬件支持的特性不同:**

例如，同为打印机，不同型号可能支持的分辨率、颜色调整方式不同，驱动程序需要在具体实现中处理这些设备特性。

**性能优化或设备限制:**
某些硬件驱动程序可能针对特定硬件进行优化，而无法在其他设备上达到一致的行为或性能表现。

60Hz  ---- 每秒 60 次**周期性变化**

revolve ：旋转

**角速度单位（转速）**

- **1 转/秒（rps, revolutions per ==second==）** = 1 Hz（赫兹）

**Hz和秒有关系** 

- 在机械、汽车、发动机、电机等领域常见，例如：
  - "电机的转速是 3000 rpm" 意味着电机每分钟旋转 3000 次。

### 坏块的处理

![image-20250312200549277](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250312200549277.png)

**“坏块对操作系统透明**”是指操作系统在使用存储设备(如硬盘或固态硬盘)时，不会直接感知到坏块的存在。这种“透明性“主要是通过存储设备的控制器和文件系统的管理来实现的。
具体来说，存储设备的控制器(例如硬盘控制器)通常内置了坏块管理机制。当设备检测到坏块时，它会将数据自动重定向到备用的良好存储区域，这称为“坏块映射“或“重映射”。因此，操作系统和应用程序仍然可以正常地读取和写入数据，而不需要意识到这些坏块的存在。

## 固态硬盘SSD

![](https://raw.githubusercontent.com/kasahuki/os_test/main/img/1741781190478.png)

![image-20250312200703835](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250312200703835.png)



![image-20250312200731061](https://raw.githubusercontent.com/kasahuki/os_test/main/img/image-20250312200731061.png)

NAND 闪存的**最小写入单位是“页”（Page）**，而**最小擦除单位是“块”（Block）**。

**固态硬盘的逻辑块不是块而是页**

！！！

SSD的写入单位是页，而擦除单位是块，块由多个页组成。当需要修改某个页的数据时，由于不能覆盖，SSD控制器会将该页的新数据写入到一个新的空闲页中
